## 2026-09-08 — [Pitfall] — ts-client / Mock 生成链路 5 个坑（schema export → codegen → MOCK_SPEC）

**类别标签**：`Pitfall`

**涉及模块**：`Directory.Packages.props` / `XiaoShuTong.Domain.csproj` / `Services\{Stats,Parent}` / `buildSchema.ps1` / `.TKWF/MOCK_SPEC.md`

**上下文**：
> 物化 Business.md 后，为生成 ts-client（GraphQL schema + codegen）与 mock 数据（MOCK_SPEC → tsclient-mock），执行 `buildSchema.ps1` 全链路，连续踩 5 个坑。全部定位并修复，链路已打通（schema.graphql 45.9KB 导出 + types.ts 68.5KB 生成 + MOCK_SPEC.md 创建）。

**决策/修复**（按踩坑顺序）：

1. **FreeSql 版本断层（CPM 3.5.310 vs 框架 refs 3.5.311）**
   - 现象：`dotnet run schema export` 抛 `Could not load file or assembly 'FreeSql, Version=3.5.311.0'`
   - 根因：项目 `Directory.Packages.props` 锁 3.5.310，框架 refs（`build\refs\Directory.Packages.props`）已升至 3.5.311 → TKWF.Domain.FreeSql.dll 绑定 3.5.311 找不到
   - 修复：项目 CPM FreeSql 系列对齐 3.5.311（FreeSql/FreeSql.DbContext/FreeSql.Extensions.Linq/FreeSql.Provider.PostgreSQL；FreeSql.Repository 保持 3.5.310 与框架一致）

2. **Dll 模式框架 DLL 不传递 NuGet 依赖**
   - 现象：3.5.311 对齐后仍缺 `FreeSql.DbContext 3.5.311` / `FreeSql.Extensions.Linq`
   - 根因：`TKWF.Domain.targets` 注释明确"框架 DLL 在 Dll 模式下不会自动传递 NuGet 依赖，需消费者显式声明"——Domain.csproj 只引了 `FreeSql.Provider.PostgreSQL`
   - 修复：Domain.csproj 补 `FreeSql` / `FreeSql.DbContext` / `FreeSql.Extensions.Linq`（版本由 CPM 统一）

3. **GraphQL 跨域同名 DTO 冲突（GetWrongQuestionsResDto ×2）**
   - 现象：`The name 'GetWrongQuestionsResDto' was already registered by another type`
   - 根因：HotChocolate 按 C# 短类名注册 ObjectType（非全名）；Learning 与 Stats 域同名 ResDto → schema 构建失败
   - 修复：Stats 版重命名 `GetWrongQuestionsResDto` → `StatsGetWrongQuestionsResDto`（对齐既有 `[GenerateController(ControllerName="StatsWrongQuestions")]` 消歧惯例）

4. **GraphQL 跨域同名 DTO 冲突（WeakPointDto ×2）**
   - 现象：`The name 'WeakPointDto' was already registered`（Services.Shared 共享版 vs Services.Parent 变体版）
   - 根因：批次 3 去重时 Parent 版因形状不同（多 Subject/StateText）保留独立，但同名仍触发 GraphQL 冲突
   - 修复：Parent 版重命名 `WeakPointDto` → `ParentWeakPointDto`

5. **buildSchema.ps1 schema export 输出路径双重拼接**
   - 现象：`DirectoryNotFoundException ...\WebApi\src\XiaoShuTong.WebApi\schema.graphql`
   - 根因：`dotnet run` 以 WebApi 项目目录为工作目录，`--output` 传相对路径被二次拼接
   - 修复：传绝对路径 `Resolve-Path(src/XiaoShuTong.WebApi)\schema.graphql`
   - 另注：脚本内 `dotnet build $WebApiProject -q` 曾现 MSB3492（obj 缓存损坏）——单独逐项目 build 修复后脚本重跑即过

**避坑指南**：
> - **Dll 模式三要素**：框架 refs 版本（build\refs\Directory.Packages.props）是 CPM 版本的唯一权威；框架 DLL 不传递 NuGet 依赖，`TKWF.Domain.FreeSql` 的 FreeSql 三件套（FreeSql/DbContext/Extensions.Linq）必须消费者显式声明；对齐后需清 obj 重建
> - **跨域 DTO 命名纪律**：HotChocolate GraphQL 类型按 C# 短类名注册——跨域同名 DTO（Res/Item）必须重命名消歧（惯例：域前缀 `{域}{ClassName}Dto`），ControllerName 消歧只解决控制器，不解决 DTO
> - **batch3 遗留确认**：WeakPointDto 共享版（Services.Shared）+ Parent 变体版（Services.Parent）命名冲突已在此修复，若后续新增跨域共享 DTO 注意 GraphQL 全局唯一性
> - **schema export 路径**：dotnet run 的 `--output` 用绝对路径，避免双重拼接
> - **MSB3492（obj 缓存损坏）**：shutdown build-server → 删 obj → 逐项目 build，勿在损坏缓存上硬跑

## 2026-09-08 — [Decision] — SG2 resolver 字段命名与"服务名"脱节（框架级问题，待框架组）

**类别标签**：`Decision`

**涉及模块**：`_TKWF/_Domain.SG/ApiService.SG/ApiServiceGenerator.Resolvers.cs`（框架）→ 影响 `src/XiaoShuTong.WebApi/schema.graphql` / `src/XiaoShuTong.WebH5/src/gql/ts-client.g.ts`

**上下文**：
> XiaoShuTong 全部 57 个领域 Service 方法统一命名为 `ExecuteAsync`（剥 Async 后均为 `execute`）。SG2 生成 GraphQL resolver 字段时直接用方法名（`method.ResolverName`），导致 schema 仅暴露 2 个业务入口，55 个服务 GraphQL 不可达。判定为框架 SG2 设计缺口，需框架组解决。

**决策/修复**：
> 完整问题分析、根因、建议方案（A 服务名前缀 / B 别名注解 / C 重名告警）、项目侧临时缓解、验证方法与验收标准，**详见独立报告**：
> 📄 `docs/草稿/SG2-resolver-命名问题-框架缺陷报告.md`
>
> 摘要：
> - 根因：resolver 字段名 = 方法名（无服务名维度），统一 `ExecuteAsync` 下必然冲突且 SG2 静默丢弃
> - 建议组合：C（重名告警止损）+ A/B（服务名前缀 / 别名注解根治）
> - 项目侧缓解：REST 通道不受影响（54 控制器全可达），UI 暂走 REST

**避坑指南**：
> - **统一 `ExecuteAsync` 命名 = GraphQL 层单点风险**：SG2 resolver 字段冲突会静默丢服务且 schema export 不报错——**必须核对 schema 字段数 vs Service 数**（本项目 4+4 vs 57）
> - 验证方法：`Select-String "type Query/Mutation"` 比对字段数；或 `gen-ts-client` 输出 `Services: N` 是否接近控制器数
> - 完整报告见 `docs/草稿/SG2-resolver-命名问题-框架缺陷报告.md`，供框架组排期处理；UI Agent 新会话使用 tkwf-tsclient 前需知悉此限制

**决策/修复**（5 类规律 + 预防清单）：

1. **Dll 模式依赖契约（坑 1/2）**：框架 refs 版本 = CPM 唯一权威；框架 DLL **不传递 NuGet 依赖**，`TKWF.Domain.FreeSql` 三件套（FreeSql/DbContext/Extensions.Linq）须消费者显式声明。**"能编译 ≠ 能运行"**——schema export / 运行启动是运行期缺依赖的暴露点。
   - ✅ 预防：新域引入框架 DLL 后，先跑一次 `dotnet run schema export` 验证运行期依赖链完整。

2. **GraphQL 类型名全局唯一（坑 3/4）**：HotChocolate 按 **C# 短类名**注册 ObjectType。跨域同名 DTO（Res/Item/WeakPoint）必然冲突，`ControllerName` 消歧只管控制器不管 DTO。
   - ✅ 预防：DTO 命名纪律从设计期执行——跨域可消费的 DTO 一律 `{域前缀}{ClassName}Dto`；共享类型入 `Services/Shared/` 且全局查重。

3. **SG2 resolver 静默丢失（坑 5，框架级）**：resolver 字段名 = 方法名，统一 `ExecuteAsync` 命名下冲突被静默丢弃，schema export 不报错。
   - ✅ 预防：**必须核对 schema 字段数 vs Service 数**（`Select-String "type Query/Mutation"` 比对）；已转交框架组（报告见 `docs/草稿/SG2-resolver-命名问题-框架缺陷报告.md`）。

4. **构建/工具链环境（坑 6/7/8）**：MSB3492 obj 缓存损坏 → shutdown + 删 obj + 逐项目 build；`dotnet run --output` 用绝对路径（工作目录=项目目录）；gen-ts-client 需 `graphql` 运行时包。
   - ✅ 预防：build 异常先 shutdown build-server；跨项目脚本传路径用 `Resolve-Path`。

5. **跨仓库 SDK 依赖（坑 9）**：`file:` 相对路径深度随目录层级漂移（DMP 2 级 vs WebH5 3 级），改用 **pnpm workspace**（`workspace:*` + `pnpm-workspace.yaml`），SDK 路径集中声明一处。
   - ✅ 预防：跨仓库本地 SDK 一律 workspace 协议，不用 `file:` 手拼深度。
