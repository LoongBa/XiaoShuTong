# 目录结构与版本管理规则

> 本文档记录 `docs/` 目录结构约定、版本级联规则和文档生命周期管理。
> 所有人类成员和 AI Agent 均需遵守。

---

## 一、版本级联关系

整个文档体系按版本链组织，从上到下驱动：

```
产品规划-V1  →  需求分析/V1/  →  架构设计/V1/  →  开发迭代/子系统/V1/
                                                      ↓
                                                部署运维/V1/
                                                使用指南-V1
```

- **升版触发**：产品规划升 V2 时，整条链同步升级
- **旧版本**：完整保留在原目录，不删除
- **跨版本引用**：开发方案引用 ADR 和架构设计时，需注明版本号

## 二、目录版本方式对照表

| 目录 | 版本方式 | 原因 |
|------|---------|------|
| `0-产品规划/` | 文件名带版本（`xxx-V1.md`） | 变动频率最低，文件少 |
| `1-需求分析/` | V1/ 子目录 | 随迭代频繁增补调整 |
| `2-架构设计/` | V1/ 子目录 | 模块间依赖多，需隔离 |
| `3-开发迭代/` | A-/B-/C- 子系统 / V1/ 子目录 | 每个子系统独立迭代 |
| `4-部署运维/` | V1/ 子目录 | 随系统版本变化 |
| `5-运营与变现/` | 文件名带版本（`xxx-V1.md`） | 跟随产品规划，文件少 |
| `6-使用指南/` | 文件名带版本（`xxx-V1.md`） | 内容不多，快照式文档 |
| `草稿/` | 无版本 | 讨论中、未定稿 |
| `adr/` | 无版本 | 一次决策，永久记录 |
| `模板/` | 无版本 | 保持最新即可 |
| `会议与决策记录/` | 无版本 | 纯存档，不修改 |

## 三、版本管理规则（MinVer）

### 3.1 版本号格式

采用 MinVer 风格：`V{major}.{minor}.{patch}`（如 `V3.1.11`）

- 目录名 `V3/` = major 版本
- 文件名 `V3.1.11-采集频率优化-开发方案.md` = 完整 MinVer 版本 + 简短标题
- 子版本自动递增：`V3.1.11 → V3.1.12`，除非显式指定版本

### 3.2 大版本 vs 小版本

| 类型 | 触发条件 | 操作 |
|------|---------|------|
| **大版本**（V3→V4） | 架构重构、产品方向调整、模块拆分合并 | 新建子目录 `V4/`，旧目录标记为 `status: 已归档` |
| **小版本**（V3.1.11→V3.1.12） | 新增功能、修复缺陷、补充细节 | 在同目录下新增文件，版本号递增 |

**大版本用子目录隔离，小版本在同目录下新增文件。**

### 3.3 开发方案与审核报告命名规则

```
<子系统目录>/V3/
├── V3.1.11-采集频率优化-开发方案.md
├── V3.1.11-采集频率优化-审核报告.md
├── V3.1.12-MCP限流修复-开发方案.md
├── V3.1.12-MCP限流修复-审核报告.md
```

`{简短标题}` 为本次版本的核心内容简称，如 `采集频率优化`、`MCP限流修复`、`新增黑马算法` 等，保持简洁、表意清晰。

### 3.4 Commit / Tag 纪律

| 规则 | 说明 |
|------|------|
| **避免频繁 commit/push** | 积累一定工作量后统一提交 |
| **tag 前置条件** | 必须有开发方案 + 审核报告均已就绪 |
| **tag 需同意** | 必须征得同意后才能打 tag，不得擅自发布版本 |

### 3.5 Tag 后微调

已 tag 版本的不重要微调，不升版本、不新建文件：

```
变更记录中追加一条：
| 2026-08-26 | tag后微调 | 修正XX参数默认值，不影响功能逻辑 | 无 |
```

## 四、每个文档的标准元数据格式

所有正式文档（非草稿）顶部 YAML frontmatter：

```yaml
---
title: 文档标题
version: V3.1.11
last_updated: 2026-08-25
status: 活跃          # 活跃 / 已归档
superseded_by:       # 被哪个版本取代，如 ../V2/
---
```

末尾变更记录表：

```markdown
## 变更记录

| 日期 | 版本 | 变更内容 | 关联ADR |
|------|------|---------|---------|
| 2026-08-25 | V3.1.11 | 初始版本 | - |
```

## 五、ADR 定位

**ADR（Architecture Decision Record）** = 架构决策记录。

- 记录一次有约束力的架构决策：问题 → 选项 → 论证 → 结论
- **不修改**，仅状态变更（活跃 → 已废弃 → 被 ADR-00X 替代）
- 独立于任何版本目录，全局可引用
- 状态总表在 `adr/README.md`

与会议记录的区别：

| | ADR | 会议与决策记录 |
|--|-----|---------------|
| 粒度 | 单次架构决策 | 整场会议所有讨论 |
| 内容 | 结论性（选项+理由+结论） | 过程性（讨论、分歧、待办） |
| 被引用 | 是，开发方案直接引用 | 否，历史存档 |
| 变更 | 不修改，仅状态变更 | 不修改 |

## 六、草稿 → 归档流程

```
草稿/  →  讨论定稿  →  拆分到各正式目录  →  原稿移入 草稿/归档/
```

- 草稿阶段：存放在 `草稿/`，无版本约束
- 定稿后：内容拆分到 `0-产品规划/`、`1-需求分析/` 等对应目录
- 原稿：移入 `草稿/归档/`，不再修改
- 归档目录中的旧版本：同级建 `归档/` 子目录存放

## 八、团队扩展性原则

1. **显式版本**：所有文档都有明确的版本标记，新人/新 Agent 可快速定位当前版本
2. **并行隔离**：不同版本目录独立，多个 Agent 可同时在 V1 和 V2 工作而不冲突
3. **完整追溯**：旧版本永不删除，历史决策可查
4. **一致性优先**：所有文档遵循同一套元数据格式，便于 Agent 解析
