# BR-17 惰性过期重邀放行 - 开发方案（V0.6.19）

## 一、背景与问题

V0.6.18 审核报告 §八 遗留项 #1：**BR-17 惰性过期副作用修正**（建议 V0.6.19+）。

### 问题现象

搭子域采用**惰性过期**语义（BR-35 物化，§3.4 状态机注）：邀请过期不落库 `Expired`，Status 列保留 `Pending`，运行时以 `ExpiresAt >= now` 判定有效。但两处查询未遵循该语义：

1. **InviteBuddyService（BR-17，L66-71）**：重复邀请检查 `existing is { Status: Pending or Accepted }` —— 只看 Status 不看 ExpiresAt。**过期 Pending 仍被命中 → 6002 阻塞对方重新邀请**。
2. **ListBuddyCandidatesService（BR-33，L64-67）**：候选排除 `b.Status is Pending or Accepted` —— 同样不看 ExpiresAt。**过期 Pending 的人仍被排除在候选列表外**（前端无法发起重邀）。

### 触发场景

A 邀请 B → B 7 天未处理 → 邀请过期（惰性，Status 仍 Pending）→ A 想再次邀请 B：
- 后端 `inviteBuddy_Execute` → 6002（BR-17 误命中过期 Pending）
- 前端 `listBuddyCandidates_Execute` → B 不在候选（BR-33 误排除过期 Pending）

即使前端绕过候选列表直接重邀，后端也会 6002。**搭子邀请对同一个人永久失效**，无解除路径（无匹配的 removeBuddy 入口）。

### 现有方案不足

- `AcceptBuddyInviteService` / `RejectBuddyInviteService`（BR-20/23）已正确：`Status != Pending || ExpiresAt < now → 6002` —— 过期 Pending 无法被 accept/reject，但**阻塞重邀**的路径缺失豁免。
- BR-35 已记录副作用但**不修正**（V0.6.18 决策：待收查询只读不触碰写路径，留待本迭代）。

## 二、修复目标

1. **BR-17 修正**：过期 Pending 不再阻塞重新邀请；Accepted 恒阻塞（关系已建立，重邀应走 removeBuddy 后再邀）；未过期 Pending 仍阻塞。
2. **BR-33 同步**：候选排除条件与 BR-17 同口径（Accepted 恒排 / Pending 未过期排），过期 Pending 的人恢复候选。
3. 保持惰性过期语义（不新增 Expired 落库、不新增过期清理 Job、不删除旧记录）——查询过滤即可，量级受 BR-15（≤10/日）+ BR-18（+7 天）约束 ≈70 条/用户。

## 三、方案设计

### 3.1 InviteBuddyService BR-17 修正（S1）

现状（L66-71）：
```csharp
var existing = await BuddiesDs.EntityGetAsync(
    x => (x.InviterId == userId && x.InviteeId == request.InviteeUserId)
         || (x.InviterId == request.InviteeUserId && x.InviteeId == userId), ct);
if (existing is { Status: BuddyStatus.Pending or BuddyStatus.Accepted })
    return new InviteBuddyResDto { Success = false, ErrorCode = BuddyErrorCodes.BuddyInviteExpired };
```

修正后：
```csharp
// BR-17：重复邀请（accepted 恒阻塞 / pending 仅未过期阻塞）→ 6002
var now = DateTime.UtcNow; // 复用 L47 已定义的 now
var existing = await BuddiesDs.EntitySelectAsync(
    x => (x.InviterId == userId && x.InviteeId == request.InviteeUserId)
         || (x.InviterId == request.InviteeUserId && x.InviteeId == userId), ct: ct);
var hasBlocking = existing.Any(b => b.Status == BuddyStatus.Accepted
    || (b.Status == BuddyStatus.Pending && b.ExpiresAt >= now));
if (hasBlocking)
    return new InviteBuddyResDto { Success = false, ErrorCode = BuddyErrorCodes.BuddyInviteExpired };
```

**为什么 EntityGetAsync → EntitySelectAsync**：同对可能残留多条记录（例：历史过期 Pending + 新 Accepted）。EntityGetAsync 取第一条，若取到过期 Pending 而实际存在 Accepted，会错误放行重邀（已建立关系被再次邀请 → 产生第二条 Pending）。EntitySelectAsync 全量取回后 Any 判定，杜绝该窗口。同对记录数极少（≤2-3），性能无碍。

### 3.2 ListBuddyCandidatesService BR-33 同步修正（S2）

现状（L64-67）：
```csharp
var excludedIds = existingPairs
    .Where(b => b.Status is BuddyStatus.Pending or BuddyStatus.Accepted)
    .Select(b => b.InviterId == meId ? b.InviteeId : b.InviterId)
    .ToHashSet();
```

修正后：
```csharp
var now = DateTime.UtcNow;
var excludedIds = existingPairs
    .Where(b => b.Status == BuddyStatus.Accepted
        || (b.Status == BuddyStatus.Pending && b.ExpiresAt >= now))
    .Select(b => b.InviterId == meId ? b.InviteeId : b.InviterId)
    .ToHashSet();
```

### 3.3 文档修订（B1，tkwf-business）

- **搭子-BR-17**：`重复邀请（存在 pending/accepted）→ 6001/6002` 修订为 `重复邀请（accepted 恒阻塞 / pending 未过期阻塞；过期 pending 豁免放行重邀）→ 6002`，注明惰性过期豁免语义。
- **搭子-BR-33**：`排除已有搭子关系（Pending/Accepted）` 修订为 `排除已有搭子关系（Accepted 恒排 / Pending 未过期排；过期 Pending 恢复候选）`。
- **搭子-BR-35**：副作用段更新——由"本轮不修正，后续迭代修正 BR-17 查询条件"改为"V0.6.19 已修正（BR-17/33 查询条件追加 `ExpiresAt >= now` 豁免过期 Pending）"，保留惰性过期语义主描述。
- **§3.4 状态机注**：保持（Expired 惰性语义不变）。
- 头部元数据：版本 v4 → v5，BR 上限搭子-36 不变（仅修订不改号），`变更` 说明本迭代修订 BR-17/33/35。
- `.TKWF/LOG.md` 追加变更记录。

## 四、范围边界

**包含**：InviteBuddyService、ListBuddyCandidatesService 两处查询修正 + Business.md 修订 + 测试补强。

**不包含**：

- ❌ 不删除历史过期记录（保留审计痕迹，查询已豁免）
- ❌ 不改 Accept/Reject（BR-20/23 已正确）

## 五、风险

| 风险 | 评估 | 缓解 |
|------|------|------|
| EntityGetAsync → EntitySelectAsync 行为差异 | 低——同对记录数极少，SQLite 内存库实测 | 新增"Accepted + 残留过期 Pending 并存仍阻塞"用例锁定 |
| 过期 Pending 重邀产生多条记录 | 低——与惰性语义一致；Accept 后旧过期 Pending 残留但不影响任何查询（均按 ExpiresAt 过滤） | BR-35 注明；不做清理（量级 ≈70 条上限） |
| 候选列表重新出现已过期但"关系事实"仍在的人 | 符合业务预期——过期邀请 = 未接受 = 无关系；重邀为全新邀请 | BR-33 修订注明 |
