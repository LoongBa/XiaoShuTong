## 三、任务 3：reject 无 [Transactional] 一致性评估（后端，tkwf-service）

### 3.1 现状（探索实证）

Buddy 域 8 个写 Service 中，**仅 AcceptBuddyInviteService 有类级 `[Transactional]`**（L19）；RejectBuddyInviteService / RemoveBuddyService / InviteBuddyService 均无。所有写操作都是**单表单行 `EntityUpdateAsync`**（无跨表写入），事务必要性本身低——但 Accept 有、Reject 没有，存在**一致性不对称**。

### 3.2 评估结论（方案决策 M-1，Oracle C2 论证修正）

**对齐加 `[Transactional]`**：成本极低（类级一行注解）。**论证**（Oracle 修正）：Reject/Remove 均为单表单行 `EntityUpdateAsync`、无计数校验（区别于 Accept 的"双方 ≤5"双 CountAsync 并发窗口）——加事务的收益是**对称性 + 维护一致性**（消除"为何 Accept 有、Reject/Remove 没有"的困惑，为未来多表扩展预留边界），**非并发安全**。不改变业务语义（BR-22/23 不变）。

**为何不改 Invite**（Oracle C2 补充）：Invite 的"查重→复用复活/新建"路径有并发风险，但 `StudyBuddies` 有 `UNIQUE(InviterId, InviteeId)` 复合唯一约束兜底（InviteBuddyService.cs:76 注释），同方向恒单记录，事务非必需——保持现状。

### 3.3 改动

1. `RejectBuddyInviteService.cs` 类级加 `[Transactional]`
2. `RemoveBuddyService.cs` 类级加 `[Transactional]`（任务 5 接线前置保障）

### 3.4 验证

- Domain build 0 错误；`tests/XiaoShuTong.Tests/Buddy/RejectBuddyInviteServiceTests.cs` 既有用例回归（BR-22/23 语义不变）

## 四、任务 4：薄弱点矩阵下钻篇目（后端扩展 + 前端，tkwf-service + tkwf-test + tkwf-tsclient）

### 4.1 现状（探索实证）

- **UI 产品定义**（UI 文档 L421）："知识点-掌握度矩阵（可下钻到具体篇目）"；V0.6.15 方案 §1.3 登记缺口："后端 GetWeaknessReport 无下钻维度（仅知识点粒度）"。
- `GetWeaknessReportService.cs`（Services/Parent/）：`GetWeaknessReportReqDto{StudentId}` → `GetWeaknessReportResDto{Success,ErrorCode,WeakPoints}` → `ParentWeakPointDto{Subject,KnowledgePoint,Accuracy,StateText}`——**仅知识点粒度，无篇目/教材位置**。
- 数据源：`KnowledgeMastery`（唯一数据源，`UserId==StudentId`，无 QuestionId/BankId/ChapterId 字段，按需聚合 Job 触发）。
- **篇目归属三层现状**：题库 JSON 有 `topic`（册/单元级）+ `knowledge_points`（篇目级，如"观沧海-背诵"）；`Questions` 实体有 `ChapterId`（如 7a）+ `KnowledgePoints`（JSONB 数组）但**无 topic/篇目名字段**；`KnowledgeMastery` 仅 Subject+KnowledgePoint。
- **已有先例**：`GetBankDetailService.cs` L46-56 "知识点树"——`questions.GroupBy(x => x.ChapterId ?? "默认")` → `TopicNodeDto{ChapterId,Title,SubTopics,QuestionIds}` 三级下钻范式。

### 4.2 方案（决策点 M-2：DTO 加字段 vs VEntity）

**采用 DTO 加字段（方案 A），不新建 VEntity**：
- 数据源单一（KnowledgeMastery 一行 → 反查 Questions），非跨表聚合报表，不满足 VEntity 适用门槛（tkwf-ventity-design 触发条件：跨表聚合/报表/跨切片消费）
- 复用 GetBankDetailService 的 ChapterId 分组先例，范式一致
- 遵守 POCO 管控：`ParentWeakPointDto` 加字段即可，不新建 POCO；不动 `Shared/WeakPointDto.cs`（注释明确"与共享版形状不同，不并入"）

**下钻路径**：`KnowledgeMastery.KnowledgePoint` → 反查 `Questions`（`KnowledgePoints` JSONB 数组包含该点）→ 得 `ChapterId` + `QuestionId` 列表 + 篇目级信息。

**字段设计（ParentWeakPointDto 增 3 字段）**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `ChapterId` | `string?` | 所属章节/单元（Questions.ChapterId，如 7a；多题不同章节取首个） |
| `QuestionIds` | `List<string>` | 该知识点下关联题目（下钻可定位到具体背诵内容） |
| `ChapterTitle` | `string?` | 章节标题（篇目名，从 GetBankDetail 同级映射或 Questions 内容镜像提取；**决策点 M-3**） |

**M-3 决策：ChapterTitle 来源**——探索显示 Questions 实体无篇目名字段，题库 JSON `topic` 未映射进实体（需 tkwf-entity 加列 + 重跑 xCodeGen + 重导题库，成本高）。本迭代**不加实体字段**：ChapterId 透出即可（前端以 ChapterId 分组展示下钻层级），篇目名富化留待题库 topic 字段映射迭代（登记延续项）。

### 4.3 前端（weakness.tsx）

- `ParentWeakPointDto` 加字段后 codegen 刷新（buildSchema + gen-mock + ts-client.g.ts）
- 页面在学科分组下增加**知识点 → 篇目（ChapterId）分组层级**：薄弱点卡点击展开/分组显示 ChapterId 下钻（产品定义 L421 "可下钻到具体篇目"）
- mock `getWeaknessReportResDtos` 补 chapterId/questionIds 字段

### 4.4 测试（tkwf-test，Parent 域 GetWeaknessReport UC）

## 七、任务 8：同年级跨群候选（后端扩展 + 前端，tkwf-service + tkwf-test + tkwf-tsclient）

### 7.1 现状（探索实证）

`ListBuddyCandidatesService` 当前筛选：Step1 反查我的群 → Step2 `myGroupIds.Contains(x.GroupId) && Role==Student && UserId != meId`（**仅同群**）→ Step3 排除已有关系 → Step4 群名映射 → Step5 去重。BR-33 明确写"同群组成员"，与 InviteBuddyService BR-16 的"同群组/同年级 OR"语义**不一致**——但注释实证"同群成员是充分子集，邀请不会触发 6006"，即当前候选是邀请合法集的子集，扩展同年级**不会破坏 BR-16 校验**。

**参考实现**：`InviteBuddyService.IsSameGroupOrGradeAsync`（L103-118）：同群 GroupId 交集 → 同年级 Groups.Grade 交集（经 GroupMembers → Groups 推导）。

### 7.2 方案

**Step2 扩展为"同群 OR 同年级"**（决策点 M-5：复用 IsSameGroupOrGradeAsync 同款推导，ListBuddyCandidatesService 内实现 `IsSameGroupOrGradeAsync` 私有方法，不跨 Service 调用）：
1. 我的群 `myGroupIds` + 我的年级 `myGrades`（Groups.Grade 去重）
2. 候选条件：`myGroupIds.Contains(x.GroupId) || (x.Role==Student && x.UserId != meId && 对方年级 ∈ myGrades)`——即同群成员 ∪ 同年级其他群学生
3. 排除规则不变（Accepted 恒排 / Pending 未过期排 / 过期豁免恢复候选）
4. 多群同人去重不变（GroupBy UserId）
5. 同年级跨群候选的展示：`groupName` 显示对方所在群名（提示跨群来源）——**决策点 M-6**：候选 DTO 已有 `groupId/groupName` 字段，跨群候选天然携带，无需加字段

**复杂度注意**：同年级跨群需要"对方年级"——先取同年级候选群的所有学生（`Groups.Grade ∈ myGrades` 的群成员），再过滤 Role=Student + 排除自己/已有关系。查询链路：Groups（Grade 过滤）→ GroupMembers（GroupId IN）→ 排除 → 去重。

### 7.3 BR 修订（tkwf-business）

- **搭子-BR-33**：`候选列表：同群组成员（Role=Student）+ ...` 修订为 `候选列表：同群组 或 同年级成员（Role=Student，OR 语义对齐 BR-16）+ ...`，注明跨群候选带对方群名。
- `.TKWF/LOG.md` 追加变更记录。
