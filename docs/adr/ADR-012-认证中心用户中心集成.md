# ADR-012 认证中心/用户中心集成（头像富化剥离）

## 状态

提议（待评审——需 Oracle/人工 + 框架扩展模块组讨论审核通过后进入迭代）

## 目的与目标

本决策要达成的目标状态：多应用共享的**认证中心 + 用户（档案）中心**（拟在 TKWF.Extension 实现，独立装配/部署）承担**集中认证、授权验证、返回用户基础信息**；各业务系统（含小书童）只消费自身所需部分，按需增强。小书童侧达成：

1. 6 个 DTO 的 `AvatarUrl` 空串桩（ListBuddies/GetRankings/GetPkResult/ListPendingBuddyInvites 等）从用户中心获取（原 P1"头像富化"剥离给外部体系，不再内部造数据）。
2. 真实微信 OAuth 登录链路（V0.6.11 登记生产配合项）由认证中心统一处理——小书童不再各自接入。
3. **双层 id 契约**：认证/用户中心对外用 **uuid**（稳定/防枚举/跨系统），业务系统内部保留 **long id**（跨表关联、View Entity JOIN 性能）——两者经映射衔接，互不干扰。

## 问题

- **问题现象**：
  1. 小书童 6 个 DTO 头像恒空串（`AvatarUrl = string.Empty` 桩）——全库无任何头像字段（`GroupMembers` 亦无），D02 架构既定"头像由外部用户体系承载"但外部体系从未实施。
  2. 登录链路是白名单 `loginByContext(userName)` 联调（V0.6.11），真实微信 OAuth（D03 §2.1 定义未实施）缺失——认证是每应用重复建设的痛点。
  3. **多应用重复建设**：同类应用若各自实现认证/头像/用户资料，成本重复、数据孤岛、口径漂移——这是本 ADR 的根因动机（用户明确："还有其它同类应用，不必都开发相同功能"）。
- **触发场景**：搭子头像、排行榜头像、PK 结果头像、待收邀请头像等展示点需要头像；新应用上线需要认证与用户资料——若各自实现，重复劳动 + 数据不统一。
- **现有方案不足**：
  1. 内部造头像数据（路径 A/B：GroupMembers 加字段 / 新建 Users 实体）违背 D02 "头像由外部用户体系承载"架构决策，且头像非真实用户头像（无真实来源）。
  2. 直接接微信 OAuth（路径 C）是 D02 正解，但每应用各自接 = 重复建设，不解决多应用复用问题。
  3. 当前 `XiaoShuTongUserInfo` 仅 `long Id`，无 uuid 字段——无法承接外部体系返回的身份。

## 使用场景

- **场景 A（认证，主路径）**：用户登录（微信 OAuth 或其它凭证）→ 认证中心签发令牌 → 各业务系统验证令牌 → 经 uuid 映射本地 long id → 填充 `DomainUser<T>` 上下文 → 后续业务查询走 long id。
- **场景 B（用户基础信息）**：业务系统展示头像/全局昵称 → 登录时公共信息进会话快照（`UserInfo` 字段，零实时调用）→ DTO 直接取值；"查看更多" → 跳转用户中心。
- **场景 C（业务信息特化）**：群内昵称（`GroupMembers.Nickname`）、亲子关系、搭子关系等**业务上下文相关信息留各子系统本地**（已实证：小书童 V0.7.2 群内昵称富化即为本地业务信息，与用户中心公共信息并存不冲突）。
- **不适用边界**：
  - 本期不实施（本 ADR 仅定集成契约与架构方向；具体设计待与框架扩展模块组讨论）。
  - 业务角色（student/owner/parent）映射由**各应用内部自行**根据返回 id 完成——用户中心不做业务角色统一（已确认）。
  - 不动小书童既有 `GroupMembers.UserId` / `ParentStudentRelations.StudentId`（long，跨表关联依赖，保留）。

## 选项

### 选项 A：认证/用户中心独立（TKWF.Extension 装配），uuid 对外 + long 对内（推荐）

- **描述**：在 TKWF.Extension 实现通用"认证中心 + 用户档案中心"能力，独立装配/部署（可作独立服务）。对外暴露 **uuid**（用户身份标识）；各业务系统内部保留 **long id**，经本地映射表（小书童对应 D02 §4.0 `Users` 最小扩展表：`Id(long) + UId(uuid) + 凭证映射`）衔接。
- **优点**：
  - 多应用复用：认证/头像/用户资料单点建设，杜绝重复开发（根因动机）。
  - 双层 id 各取所长：uuid 对外（防枚举/跨系统稳定），long 对内（跨表关联/View Entity 性能）。
  - 与小书童 D02 架构决策完全吻合（"头像由外部用户体系承载"落地；§4.0 Users 表设计正是双 id 映射承接点）。
  - 业务信息特化能力保留：各子系统按需增强（群内昵称等留本地）。
- **缺点**：
  - 需 TKWF.Extension 新增模块（认证令牌验证适配器 + 用户信息获取）——框架侧开发。
  - 小书童需实体化 `Users` 最小扩展表 + `XiaoShuTongUserInfo` 加 uuid 字段 + 登录链路替换（消费端改造）。
  - 4 个集成契约决策点待定（见决策节）。

### 选项 B：小书童内部自建账户域（Users 实体 + 头像字段）

- **描述**：不依赖外部体系，小书童内部新建 Users 实体含头像字段，所有 DTO 从本地取。
- **优点**：改动局部、无框架依赖、即时闭环。
- **缺点**：违背 D02 "头像由外部用户体系承载"架构决策；多应用各自建设重复（不解决根因）；头像无真实来源（非微信用户头像）。

### 选项 C：直接接微信 OAuth（不建用户中心）

- **描述**：小书童直接实现微信 OAuth 登录，头像从微信用户信息接口取。
- **优点**：头像真实；无需框架扩展模块。
- **缺点**：每应用各自接 OAuth = 重复建设；多应用头像/用户资料仍无统一口径；认证逻辑分散。

## 决策

选定：**选项 A（认证/用户中心独立，TKWF.Extension 装配；uuid 对外 + long 对内）**

理由：
1. **根因匹配**：多应用共享认证/用户资料是本 ADR 动机，选项 A 单点建设根治重复（B/C 均为每应用各自实现）。
2. **架构吻合**：D02 既定"头像由外部用户体系承载" + §4.0 Users 表双 id 设计——选项 A 是该架构决策的落地形态。
3. **双层 id 最优**（已讨论确认）：uuid 对外（不可枚举/跨系统稳定）、long 对内（跨表关联/View Entity JOIN 性能）——各取所长，映射衔接。
4. **业务特化保留**：各子系统保留本地业务信息（群内昵称/关系），"查看更多跳转用户中心"——信息分层清晰。

**集成契约决策点（待与框架扩展模块组具体设计时敲定，本期不实施）**：

| # | 决策点 | 讨论倾向 | 说明 |
|---|--------|---------|------|
| D1 | **uuid 发号权** | 认证中心统一发（全局唯一） | 避免多系统各自生成冲突 |
| D2 | **uuid ↔ long 映射时机** | 登录时动态映射 + 本地 Users 表持久化 | 小书童 `Users` 表（Id long + UId uuid）承接；业务查询全走 long |
| D3 | **令牌携带** | uuid 进令牌声明 → 业务系统取 uuid 再映射 | 需 TKWF.Extension 令牌验证适配器（认证中心令牌 → `DomainUser<T>` 上下文） |
| D4 | **用户信息获取策略** | 登录时公共信息进会话快照（零实时调用） | 6 DTO 头像从 UserInfo 取，避免每次实时调用户中心 |

**架构分层（已确认）**：

```
认证中心/用户中心（uuid 对外）
   │ 令牌 + 用户基础信息（头像 URL/全局昵称）
   ▼
业务系统 Users 映射表（Id long + UId uuid）
   │ 本地映射
   ▼
GroupMembers.UserId 等（long，跨表关联）—— 业务信息（群内昵称等）留本地
```

## 后果

- **正面**：多应用认证/头像/用户资料单点复用；小书童 6 DTO 头像空串桩真实闭环（从用户中心取）；真实微信 OAuth 登录由认证中心统一处理；D02 架构决策落地。
- **负面影响 / 风险**：
  - 框架侧新增 TKWF.Extension 模块（认证/用户中心）——依赖框架扩展模块组排期。
  - 小书童消费端改造（Users 实体化 + UserInfo 扩展 + 登录链路替换）——需独立开发方案。
  - uuid↔long 映射的一致性/迁移风险（现有 long UserId 与认证中心 uuid 的对应建立）。
  - 用户中心可用性影响业务系统登录（需令牌验证适配器降级策略）。
- **后续待办**：
  - ADR-012 审核通过 → 与框架扩展模块组对接具体设计（D1-D4 敲定）→ 框架侧 TKWF.Extension 开发 + 小书童侧独立方案实施。
  - 原 P1"账户域头像富化（档 C）"并入本 ADR 落地（不再独立）。
  - 原 P1"真实微信 OAuth 登录链路"并入认证中心落地。
  - 原 P1"role 契约补全（extensions 透出 role）"相关——业务角色映射由各应用内部完成（本 ADR 确认）。
