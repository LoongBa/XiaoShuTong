# ADR-010 任务进度联动契约（BR-24 TaskAssignments.Progress）

## 状态

活跃（2026-09-24 V0.6.0 开发方案 Oracle 评审闭环后转活跃；决策二"实现"行有勘误见"后果"节）

## 目的与目标

**目标**：落地学习-BR-24"同步派生：TaskAssignments.Progress 更新；全部完成 → Status=Completed"，使任务进度从"全仓无写入方"（当前 `Progress` 仅 CreateTaskService 初始写 0，`Status` 的 InProgress/Completed 两态死态）变为学生作答驱动自动推进。**达成状态**：学生每答一题（消费该题）→ SubmitAttemptService 同步推进对应 TaskAssignments.Progress（重算式，天然幂等）→ 全部题目消费 → Status=Completed + CompletedAt 写入 → 群主看板/周报/执行率等既有只读消费方激活。3 句话内：本 ADR 定"任务进度由作答事件驱动派生"的跨域写契约（完成口径 + 状态迁移 + 幂等），使 V0.6.0 迭代闭环任务进度链路。

## 问题

**问题现象**：
1. **Progress 全仓无写入方**：`TaskAssignments.Progress`（完成度 0-100）仅 `CreateTaskService:114-122` 初始写 0；`Status` 四态中 `InProgress`/`Completed` **无任何写入方**（仅 Pending=Create、Overdue=TaskOverdueScanJob）→ 群主看板执行率恒 0、周报平均进度恒 0、任务卡 Progress 恒 0、家长报告"有完成任务"恒 false。
2. **BR-24 原文仅 22 字**：`学习-BR-24 同步派生：TaskAssignments.Progress 更新；全部完成 → Status=Completed`——无法支撑 5 个实现口径决策（计数方式/完成判定/统计窗口/状态迁移/三预留字段接线）。
3. **状态机缺口**：Business.md §3.3 规定 `Pending → InProgress（创建会话）→ Completed（全部完成）`，但 `CreateStudySessionService` 从未写 InProgress（注释"切片 04 不实施"）→ 若只在 SubmitAttempt 写 Progress 会产生 `Progress>0 && Status=Pending` 状态不一致。
4. **BR-23 冲突**：任务-BR-23 允许 Overdue 状态继续复习（AllowRedo），状态机 §3.3 未规定 `Overdue→Completed` 是否允许——BR-24"全部完成→Completed"与 BR-23"逾期不改变"存在分歧。

**触发场景**：学生端任务会话作答第一题起（V0.6.0 接线后）；群主查看任务执行率/周报；任务全部完成时状态闭环。

**现有方案不足**：无实现（Progress 无写入方）；BR-24 语义单薄；状态机缺 InProgress 触发与 Overdue→Completed 边界。

## 使用场景

**适用场景**：
- S1：任务会话作答——`SubmitAttemptService` 每次有效作答（非 Full 早退/非 Play 场景/非幂等命中）后推进 Progress
- S2：任务全部完成——Progress 达 100 → Status=Completed + CompletedAt 写入
- S3：群主侧消费——`GetOwnerDashboardService` 执行率、`ExportWeeklyReportService` 周报、`ListMyTasksService` 任务卡 Progress 激活
- S4：续做/重做——BR-05 续做幂等复用会话、BR-23 逾期复习，进度跨会话聚合不回退
- S5：个人会话（TaskId=null）——不推进（无任务归属）

**不适用边界**：
- ✗ 不改变 SubmitAttempt 判题契约（五键契约不动，仅新增派生写）
- ✗ 不联动 EndStudySessionService（ADR-009 明确 Progress 归 SubmitAttempt，会话收尾只写 EndedAt 三字段）
- ✗ 不处理任务题集变更（QuestionIds 变化后进度重算基准，V0.6.0 不涉及任务编辑）
- ✗ 不改 CreateTaskService 分配逻辑（BR-05 全组分配唯一性既有）

## 决策

### 决策一：计数方式——重算式（非增量）

- `Progress = Round(consumedCount / totalCount * 100)`，其中：
  - `consumedCount` = `Attempts.Where(TaskId 关联).GroupBy(QuestionId).Count()`（跨会话聚合，TaskId+UserId 定位）
  - `totalCount` = `Tasks.QuestionCount`
- **重算而非增量**：天然幂等（BR-27 幂等命中不新增 Attempt → 重算不变）、抗重做/重发漂移、无需回退逻辑
- 查询成本：单任务题量 ≤ 50（QuestionCount 10/20/30/50），`GroupBy` 内存聚合量级合理

### 决策二：完成判定口径——"题目消费"= Correct 或达 MaxAttempts 上限

- 单题"消费"判定：`Result == Correct` **或** `AttemptCount >= MaxAttempts(2)`（对应 SubmitAttemptResDto.ShowAnswer 达上限展示答案语义——"前端展示后必进下一题"契约）
- 与引导死循环防护同构：NeedsGuidance=false（Correct 或达上限）即消费；Wrong 未达上限（NeedsGuidance=true）**不计数**（学生还在该题重试中）
- 实现：`consumedQuestionIds = attempts.Where(a => a.Result == Correct || a.AttemptCount >= 2).Select(a => a.QuestionId).Distinct()`

### 决策三：统计窗口——跨会话聚合（TaskId+UserId）

- 定位：`session.TaskId`（StudySessions）→ `TaskAssignments.Where(TaskId && UserId)`（BR-05 唯一）
- 统计 `Attempts`：**该用户该任务全部会话**（含已结束），非仅当前会话——支持 BR-05 续做幂等（二次进入同会话）+ BR-23 逾期复习（Overdue 会话继续作答不导致进度回退）
- 依赖 Attempts 的 `SessionId → StudySessions.TaskId` join 确定归属；Attempts 无 TaskId 字段（DOMAIN_MAP 确认），需经 SessionId 桥接

### 决策四：状态迁移——InProgress 由首次推进触发，Overdue→Completed 允许

- **InProgress 触发点（缺口 A 闭环）**：不在 CreateStudySession（避免"创建会话即推进"误触发），改为 **SubmitAttempt 首次推进时**——`assignment.Status == Pending → InProgress`（首次消费题即进入进行中）
- **Overdue→Completed 允许（缺口 B 闭环）**：BR-23"逾期任务仍可复习"语义下，若复习后全部完成 → 迁 Completed（进度闭环优先）；状态机 §3.3 修订为 `Pending/Overdue → InProgress → Completed`，且 `Overdue + 全部完成 → Completed`（非 Overdue 扫描变更，是作答驱动变更——不冲突 BR-22 逾期扫描仅针对未完成）
- **Completed 幂等**：`Status == Completed` 后不再变更（AllowRedo 重做不改变 Completed，对齐 BR-23）

### 决策五：三预留字段接线 + C-18 边界修订

- `TaskAssignments.SessionId`（当前会话 Id）首次推进时写入；`StartedAt`（首次推进时间）；`CompletedAt`（置 Completed 时）
- **C-18 边界修订**：`C-18 只读消费方不反向写源` 增补例外——"任务进度（TaskAssignments.Progress）由学习作答事件驱动派生（BR-24），属源事件消费方写派生物，非反向写源"；C-20 派生表补列 TaskAssignments.Progress
- Business.md 同步修订：BR-24 补全判定口径、§3.3 状态机补 InProgress/Overdue→Completed 边、L420 补 Draft 枚举（TaskStatus Draft 实存未启用）

### 决策六：Hint 补写数据源（join 卡片，不改 schema）

- 采用 **join 卡片链路**（用户确认）：题目 `meta.knowledge_card_id → 背景钩子-知识卡片.json fields.记忆钩子` → 写入 Questions.Hint
- 不改 question.v1.json schema（维持 v1.1，additionalProperties:false 无 hint 内联）；DOMAIN_MAP L347 Hint 来源描述修正为"经 knowledge_card_id join 背景钩子卡片"
- 主线：新增 JSON 四件套批量导入（读 `*-背诵内容.json`，Hint 经卡片 join）；辅线：`Hint IS NULL` 存量回填 Job
- 范围：V0.6.0 语文全覆盖（7-9 年级 130/130 + 小学 67/92）；其他学科背景钩子仅 md → 列入后续项
- 顺带修复：`Content` 镜像补 `cardType/card`（GetKnowledgeCardService 现状读 Content 的 card 字段，导入行必返回空卡片）

## 备选方案

- **增量计数**（Progress += 步进）：需处理重试/重做回退、幂等命中重复推进 → 弃，选重算（决策一）
- **仅当前会话窗口**：续做会进度回退（二次进入新 Attempts 但旧会话不统计）→ 弃，选跨会话（决策三）
- **CreateStudySession 触发 InProgress**：创建会话即 InProgress 但未答任何题，语义过早；且续做幂等复用时不重复触发 → 弃，选首次推进（决策四）
- **Overdue 不迁 Completed**：BR-23 逾期复习全部完成仍 Overdue，进度闭环缺失（看板执行率永远不含逾期完成任务）→ 弃，允许迁（决策四）
- **Hint 内联 schema 升版 v1.2**：需同步题库建设规范 + 存量 JSON 全量补 hint 字段 + 版本化迁移，工作量大且 ADR-006 版本化负担 → 弃，选 join 卡片（决策六）

## 后果

- **正面**：① 任务进度链路全通（作答→进度→状态→看板/周报/家长报告激活）；② 重算幂等（抗重做/续做漂移）；③ 跨会话窗口支持 BR-05/BR-23；④ InProgress/Completed 两态激活；⑤ Hint 补写使引导分支有真实线索（语文全覆盖）；⑥ Content card 镜像修复顺带激活 GetKnowledgeCardService。
- **勘误（2026-09-24 Oracle 评审闭环）**：决策二"实现"行 `attempts.Where(a => a.Result == Correct || a.AttemptCount >= 2)` 中 **`a.AttemptCount` 字段不存在**（Attempts 实体无此列，DOMAIN_MAP L81-98 确认）——应改为 `taskAttempts.GroupBy(a => a.QuestionId).Where(g => g.Any(a => a.Result == Correct) || g.Count() >= MaxAttempts)`。"达 MaxAttempts"按题分组计数判定，决策语义（Correct 或达上限计消费）不变。
- **负面/风险**：① SubmitAttemptService 新增跨域写（学习域→任务域），是 C-18 例外——已在决策五留痕 + Business.md 修订；② 完成判定口径（Correct||AttemptCount>=2）若与产品语义偏差需后续微调（可配置）；③ 重算跨会话聚合查询成本（单任务 ≤50 题量级可控）；④ JSON 导入新管线（导入器 + schema 校验）工作量中等；⑤ 存量回填 Job 对链路 A/B 产物（txt/AI 草稿，无 knowledge_card_id）无效——只能覆盖新 JSON 导入行，语文存量 txt 导入行需按 QuestionId/KnowledgePoint 反查卡片补齐（部分可行）。
- **后续待办**：其他学科背景钩子 md→JSON 结构化；任务题集变更后的进度重算基准；O4 连线组件（题库 O4 数据成规模后）。
