# ADR-011 微信支付回调基建

## 状态

提议（待评审——需 Oracle/人工讨论审核通过后进入迭代）

## 目的与目标

本决策要达成的目标状态：家长端"确认支付"从占位提示（`alert('支付功能即将上线')`）变为**真实微信支付闭环**——前端下单拿支付参数（H5 支付 mweb_url）→ 微信收银台 → 支付回调签名验证 → 激活订阅（`ActivateSubscriptionService` 置 Active + 周期推进）。落地后家长可真实付费开通月付（¥10/月）与年付（¥100/年）订阅，V0.6.12 登记的生产配合项（**原文："微信支付回调基建 + 前端支付下单"**，见 `docs/V0.6.12-家长端付费流程真实化-开发方案.md` §七）闭环。

> **本期范围（Oracle R5）**：仅 **H5 支付**（外置浏览器，`mweb_url` 拉起收银台，**不需要 openid**）。JSAPI/小程序支付需 openid，而当前登录是白名单 userName（V0.6.11，`login.tsx` 用 `mock-wechat-openid`），**无 OAuth→openid 链路**（D03 §2.1 定义但未实施，V0.6.11 登记"真实微信授权流程=生产"）——JSAPI/小程序登记为后续端型（待 OAuth 链路就绪）。

## 问题

- **问题现象**：家长端 dashboard "确认支付"按钮（L449-459）仅 `alert('支付功能即将上线，可先免费试用 7 天')` 占位，**无真实支付开通 mutation**。付费订阅（BR-08/09/10 激活逻辑）后端已实现但无入口可达——`ActivateSubscriptionService` 是 Callee（无 `[GenerateController]`，WARN004 登记"支付回调 Callee，有意不暴露"），前端无任何支付端点可调。
- **触发场景**：家长想付费开通订阅 → 点击"确认支付" → 仅弹提示，无法完成支付。产品付费转化链路断裂。
- **现有方案不足**：
  1. `ActivateSubscriptionService.ExecuteAsync(ActivateSubscriptionReqDto{ParentId,StudentId,Plan})` 接受明文参数直接激活——若前端可直调，任何请求可**伪造开通**（当前 BR-09 实现仅靠"已 Active 且未过期"状态判定，无支付流水号校验）。这正是该服务保持 Callee 不暴露的原因。
  2. 无下单链路：无订单实体、无支付参数生成（`prepay_id`/`mweb_url`）、无支付参数返回。
  3. 无回调端点：WebApi 无任何支付回调接收（schema 搜 Pay/Callback/Notify 零命中）。
  4. 无签名验证：微信支付 v3 回调需验签（APIv3 密钥 + 平台证书），零现状。
  5. `Subscriptions` 实体无支付字段（`TransactionId`/`OutTradeNo`/`PayTime`/`PayChannel`/`Amount`），无法关联支付流水。

## 使用场景

- **场景 A（主路径，本期）**：家长订阅开通（H5 支付）——订阅弹窗选月付/年付 → "确认支付" → 下单服务生成微信 H5 支付参数（`mweb_url`）→ 前端拉起收银台 → 支付成功 → 微信服务器回调 → 验签 → `ActivateSubscriptionService` 激活 → 前端轮询/刷新订阅状态变 Active。
- **场景 B（续费/周期推进，本期）**：已 Active 订阅的家长再次支付（新订单）→ 回调激活走周期推进分支（`PeriodEndAt` 在现有周期末基础上 +1 月/+1 年，ActivateSubscriptionService L62 分支）——**注意区别于重复回调**（重复回调=同订单重放，续费=新订单+同订阅推进）。
- **场景 C（幂等重放，本期）**：同一订单重复回调（微信 v3 失败/超时重试最多 8 次）→ 幂等处理（OutTradeNo/TransactionId 唯一约束 + 订单 Status=Paid 判定）不重复推进周期（BR-09 强化）。
- **场景 D（对账，后续）**：订单与订阅关联（OutTradeNo/TransactionId 落库），支持后续对账与客服核查。
- **不适用边界**：
  - 本期不做 JSAPI/小程序支付（需 OAuth→openid 链路，未实施；登记后续端型）。
  - 不做提现/退款（无退款产品需求，后续迭代）。
  - 不做 App 内购/支付宝/银联等多渠道（本期仅微信支付 H5，多渠道属扩展点）。
  - 不替换现有"免费试用 7 天"（startTrial）路径——试用与付费并存。
  - 本期不实施微信 OAuth 登录链路（依赖 V0.6.11 登记的生产登录配合项）。
  - 生产真实微信授权登录仍由既有白名单联调放行过渡（本 ADR 只解决支付，不解决登录）。

## 选项

### 选项 A：WebApi 独立 Controller（回调）+ Domain 下单 Service（推荐）

- **描述**：
  - **下单**：新增 Domain Service `CreatePaymentOrderService`（tkwf-service，`[GenerateController]` 暴露）——入参 `{StudentId, Plan}`，生成订单（新 `PaymentOrders` 实体），调微信统一下单 API（H5 支付）拿 `mweb_url` 支付参数返回前端。
  - **回调**：WebApi 新增独立 Controller（`PaymentCallbackController`，非 TKWF Service 链路）——接收微信 v3 原始报文（XML/JSON + 签名头），验签（APIv3 密钥解密 + 平台证书公钥验签），验签通过后 `DomainUser.Use<ActivateSubscriptionService>().ExecuteAsync(...)`（Callee 直接调，保持不暴露）。**形态对齐 D03 §11.2（`POST /api/v1/subscriptions` 已定义为"微信支付成功回调"REST 端点）**。
  - **幂等**：新建 `PaymentOrders` 实体含 `OutTradeNo`（微信商户订单号）+ `TransactionId`（微信支付交易号），**数据库唯一约束**（BR-09 强化 + C-17 跨实体约束"支付回调幂等"落地）。
- **优点**：
  - 回调端点特性与微信对接形态完全契合（原始报文 + 验签头不经 GraphQL/REST 契约化序列化层）。
  - `ActivateSubscriptionService` 保持 Callee（不暴露 = 防伪造开通）；回调 Controller 是唯一调用方。
  - 下单走 TKWF 标准 Service 链路（契约/测试/错误码体系复用）。
  - 职责分离：下单（领域层）与回调（传输层）解耦。
- **缺点**：
  - 回调 Controller 不经 TKWF Service 拦截器（事务/日志需自行处理或在 Service 内 `[Transactional]` 兜底——ActivateSubscriptionService 已有类级 `[Transactional]` ✓）。
  - 需新增 NuGet 依赖（微信支付 SDK）——**外部依赖变更，本 ADR 一并决策**。

### 选项 B：全走 TKWF Service（回调也挂 `[GenerateController]`）

- **描述**：回调作为 TKWF Service 暴露，`[GenerateController]` 挂上；验签逻辑放 Service 内。
- **优点**：单一链路（拦截器/事务/AOP 全复用）。
- **缺点**：**TKWF 契约化层（GraphQL+REST 自动生成）剥离 HTTP 原始报文与签名头**——微信回调的原始 XML/JSON + 签名头无法经 DTO 序列化层透传；`ActivateSubscriptionService` 若挂 `[GenerateController]` 则**暴露伪造开通风险**（任何人可直调激活订阅）。回调本质是 HTTP 传输层特性，硬塞 TKWF Service 链路与本框架形态冲突。

### 选项 C：ActivateSubscriptionService 直接挂 `[GenerateController]` 让前端直调

- **描述**：最小改动——把 Callee 转对外 RPC，前端"确认支付"直调。
- **优点**：改动最小。
- **缺点**：**激活契约无支付真实性证明**（根因）——任何请求带 `{ParentId,StudentId,Plan}` 即激活订阅，签名验证是支付真实性的唯一保证，C 让前端直调 = 无真实性证明的开通，付费形同虚设；生产不可接受。

## 决策

选定：**选项 A（WebApi 独立回调 Controller + Domain 下单 Service + Callee 保持不暴露）**

理由：
1. 安全（防伪造开通）：`ActivateSubscriptionService` 保持 Callee，唯一调用方为验签后的回调 Controller——支付真实性由签名验证保证，非前端可信。
2. 形态契合：微信 v3 回调是原始报文 + 签名头，独立 Controller 是唯一可行接收形态（选项 B 被 TKWF 契约化层形态排除）；对齐 D03 §11.2 既定端点。
3. 幂等强化：OutTradeNo/TransactionId 唯一约束使 BR-09 从"状态判定"升级为"流水号幂等"——重复回调/并发回调安全（C-17 跨实体约束落地）。
4. 扩展性：PaymentOrders 实体支撑对账（场景 D）。

**子决策**：
- **D1 签名验证（Oracle 定稿：官方 SDK）**：采用微信支付 v3 API 验签（APIv3 密钥 AES-256-GCM 解密 + 微信平台证书 RSA-2048-SHA256 验签 + 平台证书自动轮换缓存）。依赖：**官方 SDK `SKIT.FlurlHttpClient.Wechat`**（成熟度：覆盖 v3 全 API + 证书轮换内置；手写需自行实现证书 12 小时轮换/重试/边界处理，生产正确性 > 最小依赖）。**版本固定策略**：PackageReference 显式版本号（不走 CPM，CPM 无此包）；传递依赖 Flurl.Http 经 TKWF refs 为 Dll 模式无冲突（V0.6.3 FreeSql.Provider.Sqlite 先例）。
- **D2 订单实体（Oracle 定稿：新建 PaymentOrders）**：新建 `PaymentOrders` 实体（订单生命周期独立于订阅：续费场景同一订阅对多笔订单，月付 12 笔/年；失败/超时订单留存对账；重复回调查订单 Status 判幂等）。最小字段集：`OrderId/ParentId/StudentId/Plan/Amount/OutTradeNo/TransactionId/Status/PayTime/PayChannel/CreatedAt`；Status 枚举 `Pending/Paid/Failed/Refunded`。
- **D3 下单端型（Oracle R5 定稿：本期仅 H5 支付）**：本期只做 **H5 支付**（外置浏览器，`mweb_url` 拉起收银台，不需 openid）——JSAPI/小程序需 openid 而当前无 OAuth 链路（V0.6.11 登记"真实微信授权=生产"），登记为后续端型（待 OAuth 链路就绪）。前端"确认支付"→ 下单返回 `mweb_url` → 拉起收银台 → 成功回调激活 → 前端轮询订阅状态（复用 `listSubscriptions_Execute`，已暴露 ✓）。

## 后果

- **正面**：付费转化链路打通（H5 支付）；订阅安全激活（签名+幂等）；对账基础（订单实体）；BR-09 强化（流水号幂等）+ C-17 落地。
- **负面影响 / 风险**：
  - 新增 NuGet 依赖（SKIT.FlurlHttpClient.Wechat + Flurl.Http）——本 ADR 批准通道。
  - 回调 Controller 不经 TKWF 拦截器——事务由 `[Transactional]` Service 兜底，需测试锁定。
  - 微信支付需要**商户号 + APIv3 密钥 + 平台证书**——生产配置与密钥管理（**沙箱配置走 `appsettings.Development.json`，生产走环境变量，密钥/证书不入库不入 git**，对齐 D06 §密钥管理）。
  - 联调限制：真实微信支付需商户平台配置；本期用**微信沙箱 + 模拟回调（自构造报文+签名）**验证验签链路，对齐既有 Development 白名单联调范式。
  - 错误码扩展（Oracle R7 定稿）：新增支付类错误码并**对齐 D03 §11 错误码分级**——`8004 下单失败 / 8005 签名验证失败 / 8006 订单不存在或状态异常 / 8007 订单已支付不可重复`。
- **后续待办**：
  - ADR-011 审核通过 → 独立开发方案（V0.7.1+）→ 实施（tkwf-entity PaymentOrders / tkwf-service 下单 / WebApi 回调 Controller / 前端 H5 支付接线 / tkwf-business BR-09+C-17 修订 / 错误码 8004-8007）。
  - JSAPI/小程序端型（待 OAuth→openid 链路就绪）。
  - 订阅取消 UI（V0.6.12 登记另一配合项）可随本迭代或后续。
