## 三、任务 T2：KnowledgeMasteryAggregationJob（批量取 mastery 建 map，中复杂度）

### 3.1 现状（源码实证）

`KnowledgeMasteryAggregationJob.ExecuteAsync` L31-96：
- L33-34：一次查全部 attempts ✅
- L56：`QuestionMeta.GetManyAsync(...)` 批量预取题目元数据 ✅（ADR-008 决策二，已防 N+1）
- L70-73：`foreach (var group in grouped)` → `MasteryDs.EntityGetAsync(x => x.UserId == userId && x.Subject == ... && x.KnowledgePoint == ...)` —— **N+1**：每知识点分组一次查询

### 3.2 改动（Oracle C1 阻塞级：批量查询须提至 ExecuteAsync 外层）

> **C1 修正**：初稿方案写"`AggregateUserAsync` 内先一次批量取该用户全部 mastery"——这仅把"每分组查"降为"每用户查"，**仍是 N+1**（N=用户数）。**正确做法**：在 `ExecuteAsync` 外层（foreach 前）一次 IN 取**全部用户的 mastery** → map → 传入 `AggregateUserAsync`（对照 RankSnapshotFreezeJob §4.2 第一步范式）。

`ExecuteAsync` 内、foreach(userGroup) 前：

```csharp
// 一次 IN 取全部涉及用户的 mastery（替代 AggregateUserAsync 内逐用户查询）
var involvedUserIds = attempts.Select(a => a.UserId).Distinct().ToArray();
var allMastery = await MasteryDs.EntitySelectAsync(
    x => involvedUserIds.Contains(x.UserId), ct: ct);
var masteryByUser = allMastery
    .GroupBy(m => m.UserId)
    .ToDictionary(g => g.Key, g => g.ToList());

foreach (var userGroup in attempts.GroupBy(a => a.UserId))
{
    try
    {
        await AggregateUserAsync(userGroup.Key, userGroup.ToList(),
            masteryByUser.GetValueOrDefault(userGroup.Key) ?? [], ct);
    }
    catch { /* BR-48 单用户失败继续 */ }
}
```

`AggregateUserAsync` 签名增加 mastery 参数，分组循环内内存查 map（替代 EntityGetAsync）：

```csharp
private async Task AggregateUserAsync(long userId, List<Attempts> userAttempts,

{

    var masteryByKey = userMastery.ToDictionary(m => (m.Subject, m.KnowledgePoint), m => m);

        var key = (group.Key.Subject, group.Key.Point);

        {
            await MasteryDs.EntityCreateAsync(new KnowledgeMastery { ... }, ct);
        }
        else

            existing.State = worstState; ... await MasteryDs.EntityUpdateAsync(existing, ct);

```

**语义保持**：BR-47（无作答跳过）/ BR-48（单用户失败不中断）/ BR-49（聚合口径）/ BR-50（按需触发）不变。幂等（全量重算 + Upsert）不变——读侧从逐分组查改为**外层一次 IN 全用户**。

### 4.1 现状（源码实证）

`RankSnapshotFreezeJob.ExecuteAsync` L43-125：
- L47-48：一次查全部 Active 群组 ✅
- L65-66：`FreezeGroupAsync` 内一次查组成员（GroupId + Role=Student）✅

- L131-133：`UpsertSnapshotAsync` → `SnapshotsDs.EntityGetAsync(x => x.UserId == userId && ScopeType==Group && ScopeId==groupUid && Subject=="All" && MetricType==metric && SnapshotDate==date)` —— **N+1**：每(成员×5 指标)一次查询

### 4.2 改动

**第一步：一次 IN 取全部成员的指标**（替代逐成员 2 次查询）：

```csharp
// 在 FreezeGroupAsync 内、逐用户循环前：
var allDaily = await DailyDs.EntitySelectAsync(x => memberIds.Contains(x.UserId), ct: ct);
var allMastery = await MasteryDs.EntitySelectAsync(x => memberIds.Contains(x.UserId), ct: ct);
var dailyByUser = allDaily.GroupBy(d => d.UserId).ToDictionary(g => g.Key, g => g.ToList());
var masteryByUser = allMastery.GroupBy(m => m.UserId).ToDictionary(g => g.Key, g => g.ToList());

// 逐用户循环内改为内存取值：
dailyByUser.GetValueOrDefault(memberId) ?? []  // 替代 DailyDs 查询
masteryByUser.GetValueOrDefault(memberId) ?? []  // 替代 MasteryDs 查询
```

**第二步：一次批量取已有快照建 map**（替代每(成员×指标) EntityGetAsync；**Oracle M1：用全键**）：

```csharp
// 在 5 指标循环前：
var existingSnapshots = await SnapshotsDs.EntitySelectAsync(
    x => memberIds.Contains(x.UserId)
         && x.ScopeType == RankScopeType.Group && x.ScopeId == group.UId
         && x.Subject == "All" && x.SnapshotDate == snapshotDate, ct: ct);
// Oracle M1：幂等键 = 全键（对齐 BR-13）；未来年级范围扩展（ScopeType 变化）时不静默取错；
// 简键 (UserId, MetricType) 因未来 UpsertSnapshotAsync 复用非 Group 范围会取错快照，驳回
var snapByKey = existingSnapshots.ToDictionary(
    s => (s.UserId, s.ScopeType, s.ScopeId, s.Subject, s.MetricType, s.SnapshotDate), s => s);

// UpsertSnapshotAsync 改为内存查 map（签名不变，键 = BR-13 全键）：
var key = (userId, RankScopeType.Group, groupUid, "All", metric, snapshotDate);  // 经查询过滤外提，实际恒命中
if (!snapByKey.TryGetValue(key, out var existing))
    await SnapshotsDs.EntityCreateAsync(...);
else { existing.MetricValue = value; existing.Rank = rank; await SnapshotsDs.EntityUpdateAsync(existing, ct); }
```

> **M1（Oracle 采纳全键）**：快照 map 键用**全键** `(UserId, ScopeType, ScopeId, Subject, MetricType, SnapshotDate)`——BR-13 明文定义的幂等键；`UpsertSnapshotAsync` 未来若复用非 Group 范围（年级范围 L20 已预告"留待扩展"），简键会静默取错；全键额外成本仅 tuple 多字段，无性能影响。

**语义保持**：BR-09（无成员/无指标跳过）/ BR-10（单范围失败不中断）/ BR-11（战力组成）/ BR-12（战绩组成）/ BR-13（全键幂等 upsert）不变。

## 五、任务 T4：BankHintBackfillJob（写侧批量更新，中复杂度）

### 5.1 现状（源码实证）

`BankHintBackfillJob.ExecuteAsync` L30-82：
- L40-41：一次查全部（或按 bankId）✅
- L42：内存过滤 Hint 空行 + Take(1000) ✅
- L75-76：`foreach question` → `QuestionsDs.EntityUpdateAsync(question, ct)` —— **N+1（写侧）**：每行一次提交

### 5.2 改动（Oracle C2：toUpdate 每 chunk 独立）

收集待更新的 question 列表 → `EntityUpdateBatchAsync` 批量提交（**toUpdate 声明在 chunk 循环体内，每 chunk 独立**，避免跨 chunk 累积超大批量）：

```csharp
foreach (var chunk in emptyRows.Chunk(BatchSize))
{
    var toUpdate = new List<Questions>(BatchSize);   // C2：每 chunk 独立 List
    foreach (var question in chunk)
    {
        // ... 卡片匹配逻辑不变（(a) 精确 (b) 包含匹配）...
        if (string.IsNullOrWhiteSpace(hint)) { unmatched++; continue; }
        question.Hint = hint;
        toUpdate.Add(question);
    }
    if (toUpdate.Count > 0)
    {
        await QuestionsDs.EntityUpdateBatchAsync(toUpdate, ct);   // Oracle M2：单事务（框架 sealed 批量写自动事务）
        filled += toUpdate.Count;
    }
}
```

**语义保持**：幂等（已回填跳过 / 不覆盖已有 Hint）不变；返回 (Filled, Unmatched, Total) 不变。

> **M2（Oracle 采纳批量单事务）**：框架 API 参考文档实证 `EntityUpdateBatchAsync` 为 sealed 单事务（CRUD 自动处理权限/审计/事务）。逐行 `EntityUpdateAsync` 各为独立原子（部分成功）；批量失败整体回滚——但 Hint 回填 Job 是**幂等全量重算**（下次执行 `emptyRows` 过滤已排除已回填行），整体回滚后重跑不产生重复处理，幂等容忍度充足。

## 十一、Oracle 评审闭环（附条件通过）

评审：Oracle1（2026-09-30）。结论：**附条件通过**。决策点/修正项逐项闭环：

| 项 | 类型 | 结论 | 落地 |
|----|------|------|------|
| M1 快照键 map 精度 | 决策点 | **采纳全键，驳回简键** | `snapByKey` 用全键 `(UserId, ScopeType, ScopeId, Subject, MetricType, SnapshotDate)`——BR-13 明文幂等键；`UpsertSnapshotAsync` 未来复用非 Group 范围（年级扩展已预告）时简键会静默取错；全键成本可忽略 |
| M2 批量写事务语义 | 决策点 | **采纳批量（单事务）** | 框架文档实证 `EntityUpdateBatchAsync` sealed 单事务（CRUD 自动处理权限/审计/事务）；Hint 回填幂等（已回填跳过），整体回滚可重跑，容忍度充足 |
| **C1 KnowledgeMastery 批量查询位置（阻塞级）** | 修正项 | **采纳，必须修** | 方案 §3.2 原"AggregateUserAsync 内批量取 mastery"仍是 N+1（每用户一次）——已提至 `ExecuteAsync` 外层一次 IN 全用户 + map 传入（对照 Rank §4.2 范式）；否则验收 grep 失败 |
| C2 BankHint toUpdate 清空时机 | 修正项 | **采纳** | `toUpdate` 声明在 chunk 循环体内（每 chunk 独立 List），避免跨 chunk 累积超大批量 |
| C3 Upsert 类写侧批量优化 | 修正项 | **附条件采纳（本轮不做，登记 P3）** | Knowledge/Rank 的 create+update 混合 Upsert 逐行写——数据量有限（知识点数/成员×5 指标）；混合写无法直接批量，需分两 List 改动大收益小；待框架 `EntityUpsertBatchAsync` 或数据量增长时推进，不阻塞本轮 |

**实施前置条件**：C1 必须在实施前落实（§3.2 已修正）。C1+C2 修正后方案可进入实施；C3 不阻塞，登记工作计划 P3。

**Oracle 风险补充闭环**：① SQLite IN 上限（测试数据 < 999 行）→ §6.2 已注明；② Job 全表扫描（`x=>true`）→ 登记 P3；③ C1 签名变更影响既有测试 → §6.2 已注明同步。
